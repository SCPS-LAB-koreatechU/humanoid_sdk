# DexHand CAN 프로토콜 v2: 수신 응답 추가

어느 보드에 무엇을 올리는지와 업로드 방법은 [UPLOAD_GUIDE.md](UPLOAD_GUIDE.md)를 보세요.

v1(dexhand_control `PROTOCOL.md`, 2026-11-03)에 손 → PC 응답 두 가지를 더한 판입니다. PC → 손 프레임(제어, 목표)은 v1과 바이트 단위로 같으므로, 기존 `HandSender`는 v2 펌웨어에서도 그대로 동작합니다(응답을 읽지 않을 뿐).

## 왜 필요한가

v1 펌웨어는 응용 계층 응답이 없어서 PC가 아는 것은 "어댑터 큐에 넣었다"까지입니다. CAN 하드웨어 ACK는 버스의 아무 노드나 보내므로(팔 모터, PC 어댑터) 손이 꺼져 있거나 빠져 있어도 송신은 성공합니다. 그래서 다음을 구분할 수 없었습니다.

- 손이 꺼짐, 배터리 방전, 커넥터 분리
- 5개 프레임 중 일부 손실(조립 실패, 20 ms 마감 초과)
- 범위 위반으로 세트 거부
- 다른 송신자가 HOLD/OFF를 보내 손이 목표를 무시하는 상태
- LEDC 출력 실패 후 래치된 상태

하드웨어는 이미 응답을 보낼 수 있습니다. ESP32 TWAI는 송신이 가능하고, 트랜시버 TXD도 ACK 때문에 연결되어 있어야 합니다. v1은 `tx_queue_len = 0`으로 일부러 막아 두었을 뿐이라, 펌웨어 수정만으로 응답을 추가할 수 있습니다.

## 응답이 보장하는 범위

| 수준 | 의미 | v1 | v2 |
|---|---|---|---|
| 0 큐 등록 | PC 어댑터가 프레임을 받음 | O | O |
| 1 버스 전달 | 아무 노드가 ACK | O(의미 없음) | O |
| 2 손 수신, 검사 | 손 ESP32가 5개 프레임을 모두 받고 범위, 마감, 순번 검사 통과 | X | **APPLIED / REJECT_*** |
| 3 출력 | LEDC 15채널 듀티 기록 | X | **APPLIED** (실패 시 OUTPUT_FAIL) |
| 4 손가락 도달 | 실제 위치, 힘 | X | **X** (ES3352는 피드백 없음) |

APPLIED는 3단계까지입니다. 손가락이 실제로 갔는지, 물체를 잡았는지는 이 손으로는 알 수 없고, 카메라나 팔 토크로 따로 확인해야 합니다.

## ID (`(function << 7) | node`, 팔과 같은 규칙)

| 방향 | 프레임 | function | 왼손 60 | 오른손 61 | DLC |
|---|---|---:|---:|---:|---:|
| PC → 손 | CONTROL | 0 | 0x03C | 0x03D | 2 |
| PC → 손 | POSE | 6 | 0x33C | 0x33D | 8 |
| PC → 손 | PING (v2) | 4 | 0x23C | 0x23D | 1 |
| 손 → PC | STATUS (v2) | 5 | 0x2BC | 0x2BD | 8 |
| 손 → PC | PONG (v2) | 3 | 0x1BC | 0x1BD | 8 |

function 3, 4, 5는 Recoil 모터의 TRANSMIT_PDO_1, RECEIVE_PDO_1, TRANSMIT_PDO_2와 같은 번호입니다. 그래서 humanoid_sdk의 `RecoilBus.ping(60)`도 손에 그대로 쓸 수 있습니다. 팔 노드는 1~10이라 충돌하지 않습니다. ESP32 수신 필터는 세 PC → 손 ID의 공통 비트로 계산하며, 0x03C, 0x23C, 0x33C의 공통 마스크는 v1과 같습니다.

## STATUS

| 바이트 | 내용 |
|---|---|
| 0 | 결과가 가리키는 순번 (POSE와 무관하면 0) |
| 1 | 결과 코드 (아래) |
| 2 | 플래그: bit0 PWM 출력 중, bit1 억제(HOLD/OFF), bit2 마지막 적용 이후 워치독 만료, bit3 RX 큐 넘침, bit4 CAN 복구됨 |
| 3 | 상세: 채널 0~14 (RANGE, CONFLICT), 모드 (CONTROL_ACK), 그 외 0xFF |
| 4~5 | 적용한 세트 수 uint16 LE (순환) |
| 6, 7 | TWAI TX, RX 오류 카운터 (255로 제한) |

| 코드 | 이름 | 보내는 때 |
|---:|---|---|
| 0x00 | APPLIED | 완성 세트가 모든 검사를 통과하고 PWM 기록 |
| 0x01 | REJECT_RANGE | 채널 값이 허용 범위 밖 (상세 = 채널) |
| 0x02 | REJECT_DEADLINE | 첫 프레임부터 20 ms 넘게 걸림 |
| 0x03 | REJECT_INHIBITED | HOLD/OFF 상태에서 목표 수신 (순번마다 1회) |
| 0x04 | REJECT_CONFLICT | 같은 순번, 같은 그룹에 다른 값 |
| 0x05 | REJECT_FORMAT | 버전 니블이 1이 아니거나 그룹 ≥ 5 |
| 0x06 | OUTPUT_FAIL | LEDC 기록 실패. PWM 끔, START/RESUME 필요 |
| 0x10 | CONTROL_ACK | OFF, START, HOLD, RESUME 처리 (상세 = 모드) |
| 0x20 | HEARTBEAT | 500 ms 동안 아무 응답도 안 보냈을 때 |

- 한 순번에 대해 결과는 한 번만 보냅니다. 거부된 세트의 나머지 프레임은 조용히 버립니다.
- 그룹이 빠져 세트가 완성되지 않으면 응답이 없습니다. PC는 "응답 없음"으로 압니다.
- 응답이 버스에서 사라진 것과 세트가 사라진 것은 다음 응답의 적용 횟수로 구분합니다. 예를 들어 횟수가 2만큼 늘었으면, 앞 세트는 적용되었고 그 응답만 사라진 것입니다.
- 송신은 블로킹하지 않습니다(`twai_transmit(..., 0)`, TX 큐 8). 큐가 차면 그 응답만 버리며 PWM은 늦추지 않습니다. 넘침과 복구 플래그는 실제로 보낸 응답에 실릴 때까지 유지합니다.

## PONG

`[0xCA, 프로토콜 버전 2, 노드, 플래그, 프로필 SHA-256 앞 4바이트]`

`kProfileSha256`의 앞 8자리를 그대로 실으므로, PC가 그 손에 어떤 보정값이 올라가 있는지 확인할 수 있습니다(왼손 c3c778d2, 오른손 c7b282e4). 예를 들어 왼손 펌웨어를 오른손 보드에 올렸으면 SDK의 enable이 거부합니다.

## 버스 부하

양손이 50 Hz로 응답하면 프레임이 초당 100개 늘고, 135비트로 근사한 점유율은 약 1.35% 늘어 합계 약 23.6%가 됩니다(v1 산정 22.3%). 손 응답 ID(0x1BC~0x2BD)는 팔 PDO(0x301~0x30A)보다 우선순위가 높아서, 손 응답이 팔 목표 프레임보다 먼저 나갈 수 있습니다. 한 프레임은 약 0.13 ms입니다.

## 검증 (2026-11-03)

- 네이티브 C++ (`g++ -std=c++17 -Wall -Wextra -Werror`): `tests/ack_test.cpp` 14개 사례 통과. 적용 응답과 순번, 범위 거부와 채널, 순번당 1회 보고, 마감 거부, 그룹 손실 시 무응답, HOLD 중 INHIBITED와 RESUME, OFF, 미지 모드와 다른 노드 무응답, PING/PONG, 유휴 시 하트비트, 워치독 플래그, 출력 실패 래치, 응답 누락 후 넘침 플래그 유지와 적용 횟수, 형식 거부
- ESP32 컴파일: Arduino-ESP32 3.3.2, `esp32:esp32:esp32`, 양손 각각 통과. 플래시 285,315 B (21%), 전역 21,152 B (6%). 연구실 기준인 3.3.12에서 다시 컴파일할 것
- 실보드 업로드, 실제 CAN 왕복, 응답 지연 측정은 하지 않음
